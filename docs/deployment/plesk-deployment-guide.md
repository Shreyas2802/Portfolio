# Deploying to Plesk (portfolio.vistrut.com)

This assumes what's already true for this project: a Plesk panel with
the `portfolio.vistrut.com` subdomain created, and a `PortfolioDb`
database already provisioned. It also assumes Plesk's Windows/.NET
Core hosting (IIS + ASP.NET Core Module) - the standard way Plesk
hosts .NET apps. **Exact menu names/navigation below may differ
slightly by Plesk version** - I can't browse your specific panel, so
treat the panel steps as "what to look for," not pixel-exact
instructions.

## 1. One-time architecture note: same-origin in production

Locally, the React app (Vite, port 5173) and the API (port 5199) are
two separate processes talking over a dev proxy. In production, this
repo is set up to serve **both from the single Portfolio.Api app** -
the built SPA lives in its `wwwroot`, and `MapFallbackToFile` (Phase
10) serves `index.html` for any route that isn't an API call or a
static file. This is the arrangement the spec itself prefers ("if
production can be hosted under the same domain/origin, prefer that")
and it means you deploy **one thing**, not two.

## 2. Build for production

From the repo root, on your Windows machine:

```powershell
.\deploy\build-and-publish.ps1
```

This builds the React app, copies it into
`apps\api\Portfolio.Api\wwwroot` (never touching `wwwroot\uploads`),
and runs `dotnet publish`. The result lands in `.\publish` - **this
folder's contents are what you upload to Plesk**, not the whole repo.

## 3. Upload to Plesk

Any of these work:
- Plesk File Manager: zip the `publish` folder's contents and extract
  them into the subdomain's document root.
- FTP/FTPS (Plesk gives you credentials for this per-subdomain).
- Plesk's Git feature (Websites & Domains → Git): point it at this
  repo, and add a deployment action that runs
  `deploy\build-and-publish.ps1` and copies `publish\*` into the
  document root after each pull. This is the closest thing to real
  CD without a dedicated deployment server.

**Whichever method you use, never let it delete or overwrite an
existing `uploads` folder in the document root** once real photos
exist there - see the Storage section below for why this matters and
how the app avoids it structurally.

## 4. Configure IIS / ASP.NET Core hosting

Plesk's .NET Core support configures IIS + the ASP.NET Core Module
(ANCM) for you when you set the subdomain's application to run as
.NET Core, pointing at `Portfolio.Api.dll` inside the uploaded
`publish` folder. Look for a ".NET Core" / "Application Pool" section
under the subdomain's hosting settings.

**Enable stdout logging** (this project's chosen monitoring approach -
see Section 8) by confirming `stdoutLogEnabled="true"` in the
generated `web.config` (it's on by default from `dotnet publish` in
newer SDKs, but verify) and that a `logs` folder exists and is
writable next to the app.

## 5. Set environment variables (secrets)

**Never** commit real values for these - they're set at the hosting
level, the same principle as .NET User Secrets locally:

| Variable | Value |
|---|---|
| `ConnectionStrings__DefaultConnection` | Real SQL Server connection string for `PortfolioDb` (see Section 6) |
| `Jwt__Key` | A long random string, 32+ characters - **different from your local dev value** |
| `Jwt__Issuer` | `PortfolioApi` (or leave matching local - just needs to be consistent) |
| `Jwt__Audience` | `PortfolioClient` |
| `AdminUser__Username` | Your real admin username for the live site |
| `AdminUser__Password` | A strong, unique password - **not the same as your local dev one** |
| `Storage__UploadsRootPath` | An absolute path **outside** the app's document root - e.g. `D:\plesk-data\portfolio-uploads` (see Section 7) |

`ASPNETCORE_ENVIRONMENT=Production` is already baked into `web.config`
by the build (Portfolio.Api.csproj) - you don't need to set it
manually, and it isn't a secret.

Set these via whichever of these Plesk exposes for your setup:
- The subdomain's ".NET Core" settings panel, if it has an
  "Environment variables" section (most current Plesk versions do).
- IIS Application Pool → Advanced Settings, if Plesk gives you direct
  IIS Manager access (Windows Server's App Pool environment variables
  feature works here too).
- As a last resort, manually add an `<environmentVariables>` block
  inside `<aspNetCore>` in the deployed `web.config` on the server -
  but note this file gets regenerated by every `dotnet publish`, so
  you'd need to redo this after every deploy unless you script it.

## 6. Production database

`PortfolioDb` already exists on Plesk. Two ways to get the schema
onto it:

**Option A - direct connection** (if your dev machine can reach the
Plesk SQL Server over the network):
```powershell
cd apps\api
dotnet ef database update --project Portfolio.Infrastructure --startup-project Portfolio.Api --connection "<the real production connection string>"
```

**Option B - generate a SQL script** (works even without direct
network access - run the script through Plesk's own database
management tool instead):
```powershell
dotnet ef migrations script --idempotent --project Portfolio.Infrastructure --startup-project Portfolio.Api --output migrate.sql
```
`--idempotent` makes the script safe to run against a database that
already has some migrations applied - it checks what's already there.

**Database permissions:** the SQL login used in the production
connection string should be scoped to `PortfolioDb` only, not a
server-wide admin account - check this in Plesk's SQL Server/database
management section (matches the pre-production checklist item
"database permissions minimized").

## 7. Storage: uploads must survive redeployment

This matters because `dotnet publish` (and most deployment methods)
replace an app's files wholesale - if uploaded photos lived inside the
published folder, **the next deployment would delete every photo
anyone ever uploaded**.

This is why `Storage__UploadsRootPath` (Section 5) should point
**outside** wherever you deploy the app to - e.g. a folder Plesk
manages separately, or a dedicated data folder on the server that
your deployment process never touches. Once set:
- The app creates this folder automatically on first run if it
  doesn't exist.
- `LocalPhotoStorageService` writes/reads/deletes there instead of
  `wwwroot/uploads`.
- The app still serves them at the same `/uploads/...` URLs regardless
  of where they physically live (`Program.cs` maps that path to
  whatever `Storage__UploadsRootPath` resolves to).

If you don't set this variable, uploads default to
`wwwroot/uploads` inside the deployed app - **fine for a first
deployment with no real photos yet, but revisit this before your first
redeploy once real content exists.**

## 8. HTTPS

Plesk's SSL/TLS Certificates section supports free Let's Encrypt
certificates per-subdomain - issue one for `portfolio.vistrut.com`.
Once issued, the app's own `UseHttpsRedirection()` (Phase 2) and HSTS
header (Phase 7, active outside Development) take care of the rest.

## 9. Verify the deployment

- Visit `https://portfolio.vistrut.com` - the homepage should load
  (this confirms the SPA fallback route is working).
- Visit `https://portfolio.vistrut.com/api/photography/albums` -
  should return JSON, not an error (confirms the API side works).
- Visit `https://portfolio.vistrut.com/api/health` - the health-check
  endpoint from Phase 2 - should show `"database": "connected"`
  (confirms the production connection string and DB are correctly
  wired up).
- Try logging into `/admin/login` with the production admin
  credentials you set in Section 5.

## 10. Monitoring

No new dependency was added for this - IIS/ANCM's built-in **stdout
logging** (enabled in Section 4) writes the app's own logs to a file
next to the deployed app, which is enough to review after an incident
without needing a separate logging service for a personal-scale site.

For uptime monitoring, point a free service (e.g. UptimeRobot,
Better Uptime's free tier) at `https://portfolio.vistrut.com/api/health`
- it already reports real database connectivity, not just "the
process is running."

## 11. Backups

- **Database:** Plesk's Backup Manager (Websites & Domains → Backup
  Manager) can include databases in scheduled backups - set this to
  include `PortfolioDb`, daily, with a retention period you're
  comfortable with.
- **Uploads folder:** since it now lives outside the app's deployment
  folder (Section 7), make sure Plesk's backup scope includes that
  path too - it won't be swept up automatically just because the site
  is backed up, since it's deliberately outside the site's normal
  document root.
- **Test the restore, not just the backup:** restore a backup into a
  differently-named scratch database and confirm the data is actually
  intact and queryable. An untested backup is a hope, not a backup -
  do this once after your first real backup exists (see the
  pre-production checklist).

## 12. CI/CD

- **CI** (already set up): `.github/workflows/ci.yml` runs on every
  push/PR - builds and tests both the backend (unit + integration
  tests, Phase 9) and frontend, plus dependency audits for both. This
  runs on GitHub's infrastructure and needs no Plesk access.
- **CD** (deployment itself): the most practical option without a
  dedicated deployment server is Plesk's own Git integration
  (mentioned in Section 3) - it can pull from this repo and run a
  deployment action script on each pull. Fully automated push-to-
  deploy (e.g. triggered directly from the GitHub Actions workflow)
  would need Plesk API credentials or SSH/FTP access configured as
  GitHub Actions secrets - a reasonable next step once the manual
  Plesk-Git flow is working reliably, but deliberately not set up here
  since it needs credentials only you have.

## Redeploying after changes

1. `.\deploy\build-and-publish.ps1`
2. Upload the new `publish` contents (Section 3) - `uploads` folder
   safety is structural now (Section 7), not something to remember
   each time.
3. If you added a new EF Core migration since the last deploy, run it
   against production (Section 6) **before** the new code goes live -
   the new code may expect columns/tables the migration creates.
4. Recycle the IIS Application Pool (Plesk's hosting panel has a
   restart/recycle action) so the new `Portfolio.Api.dll` actually
   gets loaded.
